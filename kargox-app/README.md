# KargoX — single Spring Boot app (backend + web UI)

This is the backend and web frontend merged into **one deployable unit**: the React app builds straight into `src/main/resources/static`, Spring Boot serves the API and the UI from the same port, and `mvn package` produces one runnable jar. Open this folder as a single project in IntelliJ and you're done — no second process, no CORS, no separate frontend server needed for a normal run.

(The React Native mobile app still can't join this — it's a separate native runtime that has to run on a phone/emulator, not inside the JVM. It stays a second project that talks to this same API over the network. See `../kargox-mobile`.)

## How it fits together

```
kargox-app/
├── pom.xml                         Maven build for the backend
├── src/main/java/com/kargox/...    Spring Boot app (same as the standalone backend)
├── src/main/resources/
│   ├── application*.yml
│   └── static/                     ← React build output lands here (gitignored, regenerated by `npm run build`)
└── frontend/                       The React app's source (this is what you edit)
    ├── package.json
    ├── vite.config.js              build.outDir points at ../src/main/resources/static
    └── src/...
```

Two new pieces vs. the standalone backend, both in `src/main/java/com/kargox/config/`:
- **`WebConfig.java`** — serves the built React files, and falls back to `index.html` for client-side routes (e.g. `/book`, `/track/5`) so direct loads and page refreshes work, without swallowing real `/api/**` 404s.
- **`SecurityConfig.java`** — updated so only `/api/v1/**` needs auth; everything else (the SPA's HTML/JS/CSS) is open, same as any static website.

## Running it (the normal day-to-day loop)

1. **Whenever you change frontend code**, rebuild it into the backend's resources:
   ```bash
   cd frontend
   npm install      # first time only
   npm run build
   ```
2. **Run the Spring Boot app** — in IntelliJ, click the green ▶ on `KargoXApplication.main()`, or `mvn spring-boot:run` from the root. One process, one port.
3. Open `http://localhost:8080` — that's the whole app, UI and API together.

There's no need to run `npm run dev` / a separate frontend server for normal use — that's only useful if you want hot-reload while actively editing frontend code (see below).

### Optional: hot-reload while editing the frontend

```bash
cd frontend
npm run dev     # http://localhost:5173, proxies /api/v1 and /ws to :8080
```
Keep the Spring Boot app running on `:8080` at the same time. Work at `:5173` for instant reload, then `npm run build` once you're happy, to bake the final version into the jar.

## Packaging a single deployable jar

```bash
cd frontend && npm run build && cd ..
mvn clean package
java -jar target/kargox-backend-1.0.0.jar
```

That jar contains the compiled backend **and** the built UI. Copy it anywhere with a JVM and run it — that's the entire app.

## Stage: real map, live location, address geocoding (added)

**Nominatim's usage policy** (https://operations.osmfoundation.org/policies/nominatim/) caps the public instance at low volume — fine for development/demo, but a production deployment doing real traffic should self-host Nominatim or move to a paid geocoding provider. The `GeocodingServiceImpl` class doc explains this.

### You need to do one thing for emails to actually send

Nothing sends by default (`kargox.mail.enabled=false`) — everything just logs to the console instead, so the app runs with zero setup. To turn real email on:

```bash
MAIL_ENABLED=true
MAIL_HOST=smtp.gmail.com
MAIL_PORT=587
MAIL_USERNAME=your-address@gmail.com
MAIL_PASSWORD=your-16-character-app-password   # NOT your normal Gmail password
```

Gmail requires an **App Password** (Google Account → Security → 2-Step Verification → App passwords) — your regular password won't authenticate. If you'd rather not use a real inbox while testing, [Mailtrap](https://mailtrap.io) or [Ethereal](https://ethereal.email) both give you a free fake SMTP inbox in about a minute — just point `MAIL_HOST`/`MAIL_USERNAME`/`MAIL_PASSWORD` at whichever one you pick.

Set these as environment variables (IntelliJ: **Run → Edit Configurations** → your `KargoXApplication` config → Environment Variables), not directly in `application.yml`, so credentials never end up committed to source control.

## Stage: PostgreSQL migration + transactional rollback safety

### Database: PostgreSQL, schema owned by Flyway

The app now runs on PostgreSQL only (H2 and MySQL support both removed) with the schema defined explicitly in `src/main/resources/db/migration/V1__init_schema.sql`, not auto-generated by Hibernate. `spring.jpa.hibernate.ddl-auto` is now `validate` — Hibernate checks every entity matches these tables/columns exactly at startup and **fails fast** if they've drifted, but never silently creates or alters anything. This is the standard "reviewable, versioned schema" pattern real production Spring Boot apps use, and directly addresses "reconstructing everything" — the whole schema is now one deliberate, readable file instead of whatever Hibernate happened to auto-generate.

**Getting a database**: `docker-compose.yml` at the project root spins one up in one command:
```bash
docker compose up -d
```
That's a Postgres 16 container with a `kargox` database, user, and password all pre-set to match the app's defaults — no further config needed for local dev. (No Docker? Install PostgreSQL locally and create a `kargox` database/user matching `application.yml`'s defaults, or override via `DB_HOST`/`DB_PORT`/`DB_NAME`/`DB_USERNAME`/`DB_PASSWORD` env vars.)

**Trade-off worth knowing**: this removes the previous "zero setup, just click run" H2 experience — you now need Postgres running (via the one-line Docker command, or a local install) before the app will start. In exchange, you get a real database with proper constraints, indexes, and a schema history instead of an in-memory one that resets every restart.

### Payment rollback: a real refund, not just a status flip

New `PaymentService.refund()` — reverses a completed payment: marks it `REFUNDED`, **claws back the driver's wallet credit** for that booking (a compensating transaction, since the driver was already paid out of the fare on completion — a real "rollback" has to undo that too, not just flip a customer-facing flag), and notifies both parties by email + in-app. All in one `@Transactional` method, so a refund is never left half-applied. Exposed to admins: `POST /api/v1/admin/bookings/{id}/refund`, with an "Issue refund" button now on completed bookings in the admin bookings page.

### What was already correct, and what I added

The write operations across the whole codebase already had `@Transactional` consistently — that groundwork was solid from early on, so "does a failure mid-operation roll back the whole thing" was already true for booking creation, status transitions, payment + driver-wallet-credit on completion, ratings, etc. What was genuinely missing:
- **The refund/rollback capability itself** (above) — there was no way to reverse a payment at all before this.
- **A friendly error for concurrent-accept races**: two drivers tapping "Accept" on the same booking within milliseconds of each other is exactly what the existing `@Version` optimistic locking (already on every entity, from the very first version of this backend) protects against — but the loser of that race was getting a raw 500 error. `GlobalExceptionHandler` now catches `ObjectOptimisticLockingFailureException` and returns a clear "this was just updated by someone else" message instead.

## Fix: LazyInitializationException breaking vehicle registration, tracking, and admin bookings

**Root cause**: switching to `spring.jpa.open-in-view: false` during the Postgres migration stage (correct, standard practice - the default silently keeps a DB connection open for an entire request) needed a follow-up I missed at the time: several read-only service methods build their response DTOs by touching **lazy-loaded** relationships (`booking.getDriver()`, `driver.getUser()`, `payment.getBooking()`, etc.), which now requires an explicit transaction boundary instead of relying on Spring's old always-open-connection behavior. Ten methods across five services were missing it: `BookingServiceImpl` (getById, getByReference, getForCustomer, getForDriver, searchAll), `VehicleServiceImpl.getForDriver`, `DriverServiceImpl` (getByUserId, getById), `RatingServiceImpl.getForBooking`, `PaymentServiceImpl.getForBooking`.

`DriverServiceImpl.getByUserId()` being unprotected is what broke vehicle registration specifically - `VehicleController.register()` calls it first to resolve the driver's ID.

**Fix**: `@Transactional(readOnly = true)` added to all ten. This is the standard, correct fix for this exact situation (not reverting `open-in-view`, which trades this bug for a worse one - connections held open through response rendering).

**Also fixed**: two places in the frontend were silently swallowing errors (`.catch(() => {})` with nothing in it, or no `.catch` at all), which is why these failures showed up as an indefinite "Loading..." instead of a message - `TrackBookingPage.jsx` and `DriverVehiclesPage.jsx` now surface whatever the server actually said.
